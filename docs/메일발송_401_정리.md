# 인증 메일이 나가지 않는다 — NCP 401 Authentication Failed

2026-09-28 발생. **2026-10-03 발송 성공, 2026-10-04 실제 수신 확인 — 완전히 해결.**

> ### 원인은 하나가 아니라 셋이었다
>
> **1. 인증키 쌍이 어긋나 있었다.** `api.env` 에 9/22 키의 액세스가 들어 있는데 시크릿은
> 그 짝이 아니었다. 메일만의 문제가 아니어서 같은 키로 Server·VPC·SENS 를 찔러도
> 전부 막혔다 (6절).
>
> **2. 그걸 고치자 두 번째 벽이 나왔다 — 엔드포인트가 틀렸다.** 같은 제품에 API 가 둘인데,
> 우리는 옛 Cloud Outbound Mailer 경로를 부르고 있었다. 이 계정은 **SENS 로 가입**돼 있어
> 옛 경로가 찾는 "기본 프로젝트" 가 없다 → `77301 default project is not exist`.
>
> **3. 그것까지 고쳐도 메일은 한 통도 나가지 않았다.** DMARC 레코드가 없어 NCP 가 발송
> 직전에 거부하고 있었다 — . 아래 "벽이 셋이었다" 참조.
>
> **벽이 겹쳐 있었다.** 앞의 것을 넘기 전에는 다음 것이 보이지 않는다. 게다가 2번을
> 넘었을 때 받은  를 "뚫렸다" 로 읽은 탓에, 3번을 하루 늦게 발견했다 —
> **202 는 접수이지 발송이 아니다.**

### 고친 것

| | 전 | 후 |
|---|---|---|
| 호스트 | `mail.apigw.ntruss.com` | `sens.apigw.ntruss.com` |
| 경로 | `/api/v1/mails` | `/mail/v2/services/{서비스ID}/requests` |
| 수신자 `type` | `"R"` | `"TO"` (`"R"` 은 `77102` JSON 파싱 오류) |
| 설정 | — | `APP_MAIL_SERVICE_ID` 추가 (`ncp:mail:kr:...`) |
| 키 | 9/22 액세스 + 짝 아닌 시크릿 | 9/28 키 쌍 |

곁들여 `AppProperties` 의 메일·문자 키에 `strip()` 을 넣었다 — `isBlank()` 는 `"키 "` 를
통과시켜 같은 증상을 만든다. 되돌아가는 것을 막으려고 `NcpMailRequestTest` 를 두었다.

**확인** — 배포된 `api.env` 값만으로 실제 발송 `202 Accepted`,
`requestId=20261003-R-01M410N17EYNP2HSPDHVABQP9D-23574`. 기동 로그에 `[MAIL]` 경고 없음.

> ⚠️ **아직 사람이 받아본 적은 없다.** 회원 2명 중 이메일을 가진 사람이 0명이라
> 앱 경로(비밀번호 찾기·가입)를 운영에서 끝까지 태울 수가 없었다. 받은 메일 원본에서
> `spf=pass`·`dkim=pass` 를 확인하는 것은 아직 남아 있다 (10절).

### 벽이 셋이었다 — 2026-10-04 추가

10-03 에 `202 Accepted` 를 받고 "뚫렸다" 고 적었는데, **그것은 접수였을 뿐이고 메일은
한 통도 나가지 않았다.** 이력을 뽑아 보니 그때까지의 발송이 전부 `FAILED` 였다.

| | 벽 | 증상 | 해결 |
|---|---|---|---|
| 1 | 인증키 쌍이 어긋남 | 401 Authentication Failed | 9/28 키 쌍으로 교체 |
| 2 | 옛 Cloud Outbound Mailer 경로 | 77301 default project is not exist | SENS 경로로 변경 |
| 3 | **DMARC 레코드 없음** | `SECURITY_AND_POLICY_ABNORMAL` | `_dmarc` TXT 추가 + 콘솔 인증 |

**NCP 는 SPF·DKIM·DMARC 가 <u>셋 다</u> 인증돼야 내보낸다.** SPF·DKIM 은 2026-09-22 에
돼 있었고 DMARC 만 비어 있었는데, 그 하나 때문에 전부 거부됐다. 수신측이 스팸으로
분류한 것이 아니라 **NCP 가 보내기 전에 막은 것**이라 스팸함에도 없었다.

```
_dmarc.hanseongge.com  TXT  v=DMARC1; p=none; rua=mailto:admin@hanseongge.com
```

넣은 뒤 **콘솔에서 [인증] 버튼을 눌러야 한다.** NCP 는 발송할 때마다 DNS 를 보는 것이
아니라, 인증 버튼을 눌렀을 때의 결과를 저장해 두고 그것으로 판단한다. 레코드만 넣고
기다리면 계속 거부된다.

2026-10-04 22:10 DMARC 인증 → 22:1x 발송 `COMPLETED / MAIL_SENT` → **수신함 도착 확인.**

### ⭐ 메일이 안 갈 때 — 사유를 NCP 에게 직접 묻는다

추측하지 말 것. 아래 세 단계로 `sendResultMessage` 가 나온다. 이것을 몰라서 이번에
"202 니까 나갔다" 로 이틀을 보냈다.

```bash
sudo bash -c '. /etc/hanseongge/api.env
AK=$APP_MAIL_ACCESS_KEY; SK=$APP_MAIL_SECRET_KEY; SID=$APP_MAIL_SERVICE_ID
g() { T=$(($(date +%s)000))
  S=$(printf "GET %s\n%s\n%s" "$1" "$T" "$AK" | openssl dgst -sha256 -hmac "$SK" -binary | base64)
  curl -s "https://sens.apigw.ntruss.com$1" -H "x-ncp-apigw-timestamp: $T" \
    -H "x-ncp-iam-access-key: $AK" -H "x-ncp-apigw-signature-v2: $S"; }

# 1) 최근 발송 (ISO 8601 + 타임존. + 는 %2B 로 인코딩해야 한다)
F=$(date -d "-2 days" +%Y-%m-%dT%H:%M:%S)%2B09:00; T2=$(date +%Y-%m-%dT%H:%M:%S)%2B09:00
g "/mail/v2/services/$SID/requests?fromDateTime=$F&toDateTime=$T2&pageSize=10"

# 2) 그중 한 건의 mailId
g "/mail/v2/services/$SID/requests/<requestId>/mails"

# 3) 수신자별 사유 ← 여기에 sendResultCode / sendResultMessage 가 있다
g "/mail/v2/services/$SID/requests/<requestId>/mails/<mailId>"'
```

| `sendResultCode` | 뜻 |
|---|---|
| `MAIL_SENT` | 나갔다 |
| `SECURITY_AND_POLICY_ABNORMAL` | SPF·DKIM·DMARC 중 하나가 인증 안 됨 |

### DKIM 셀렉터는 `ncpcompubkr` 다

한국(KR) 환경의 고정 셀렉터다. 호스트는 `ncpcompubkr._domainkey.<도메인>`.
서명값이 392자라 DNS TXT 한도(255자)를 넘으므로 **큰따옴표로 나눠 등록**해야 한다
(Global DNS 는 자동으로 나눠 준다).

> 이것을 몰라서 셀렉터 15개를 찍어 보고 "DKIM 이 없다" 고 두 번 단정했다. 실제로는
> 처음부터 제대로 들어가 있었다. **없다고 말하기 전에 공급자 문서에서 이름 규칙부터
> 찾을 것.**

## 4. 엔드포인트는 살아 있다

콘솔 메뉴에서 Cloud Outbound Mailer 가 안 보여 "제품이 없어진 것 아니냐"는 의심이 있었으나,
**게이트웨이 응답이 아니라고 말한다.**

```bash
curl -s https://mail.apigw.ntruss.com/api/v1/mails
{"error":{"errorCode":"300","message":"Not Found Exception","details":"URL not found."}}

curl -s -X POST https://mail.apigw.ntruss.com/api/v1/mails
{"error":{"errorCode":"200","message":"Authentication Failed",
          "details":"Authentication information are missing."}}   ← 401
```

읽는 법:

- `GET` 은 404 — 그 경로에 GET 메서드가 없을 뿐이다. **제품 유무와 무관하다**
- `POST` 는 401 — **경로가 살아 있고 인증 단계까지 도달한다.** 없어진 주소는 404 를 주지 인증 실패를 주지 않는다
- 헤더 없이 부르면 `missing`, 우리 앱은 `invalid` — 즉 **우리는 헤더를 제대로 보내고 있고 NCP 가 그 값을 거부한다**

공식 문서도 같다:

- SENS API 문서에는 **메일 API 가 없다** (SMS·알림톡·브랜드 메시지 셋뿐)
- Cloud Outbound Mailer API 문서는 살아 있고 `POST /api/v1/mails` 그대로다
- **serviceId 를 받지 않는다.** serviceId 는 SENS 의 SMS·Biz Message 쪽 개념이다

콘솔 메뉴가 개편되어 안 보이는 것과 API 가 없어진 것은 다른 이야기다.

## 5. 우리 구현은 문서와 일치한다 (대조 결과는 6절)

`NcpApiSigner.sign()` — [`NcpApiSigner.java:24-29`](../backend/src/main/java/com/hanseongge/domain/notification/NcpApiSigner.java)

```
StringToSign = "POST /api/v1/mails\n" + timestamp + "\n" + accessKey
signature    = Base64(HmacSHA256(secretKey, StringToSign))
```

헤더 4종 — `Content-Type`, `x-ncp-apigw-timestamp`, `x-ncp-iam-access-key`, `x-ncp-apigw-signature-v2`.
NCP 문서 예시와 같다. **코드를 고칠 이유가 없다.**

## 6. 게이트웨이 오류 문구 사전

2026-10-03. 먼저 키 없이 **바깥에서** 게이트웨이를 여러 모양으로 찔러 `details` 문구를 모았다.

| 보낸 것 | `details` |
|---|---|
| 헤더 3종 중 하나라도 빠짐 (빈 값 포함) | `Authentication information are missing.` |
| 타임스탬프가 과거·미래로 많이 벗어남 | `Expired timestamp.` |
| **모르는 액세스 키** | `This account is not allowed.` |
| ← **우리 앱이 받는 것** | `Invalid authentication information.` |

"모르는 액세스 키" 는 **열한 가지 모양**으로 확인했다 — 포털형 20자, `ncp_iam_BPASKR`·`BPKSKR`·`BPAMKR`·
`XXXXXX` 접두사, 구분자 없는 `ncp_iam_` + 20자, 꼬리 공백이 붙은 키, 그리고 각각에 깨진 서명·짧은 서명.
**전부 `This account is not allowed.`** 였다. 즉 게이트웨이는 계정을 먼저 찾고 그 다음에 인증을 본다.

> ### 여기서 얻는 것 하나
> 우리 액세스 키는 **NCP 에 실재한다.** 가짜로는 이 문구를 만들 수 없었다.

### ⚠️ 정정 — 이 문구로 "서명이 틀렸다"고 단정할 수 없다

처음에 위 사전만 보고 "계정은 통과하고 서명에서 떨어진다" 로 읽었는데, **그건 과한 독해였다.**
서버에서 실제 키로 대조해 보니:

| 보낸 것 | 결과 |
|---|---|
| 진짜 액세스 키 + **일부러 틀린** 서명 | `Invalid authentication information.` |
| 진짜 액세스 키 + **제대로 계산한** 서명 | `Invalid authentication information.` — **같다** |

둘이 구분되지 않는다. 그래서 이 문구는 "서명 검증 실패" 를 **가리키지 않는다.**
우리가 보내는 인증 정보가 통째로 거부된다는 뜻까지만 말한다.

### 서버에서 실제로 측정한 것

`api.env` 의 값을 그대로 써서 (셸 변수를 `"$VAR"` 로 감싸서) 여러 제품을 찔렀다.

| 제품 / 경로 | 결과 |
|---|---|
| 메일 `POST mail.../api/v1/mails` | 인증에서 거부 |
| Server VPC `GET /vserver/v2/getRegionList` | 인증에서 거부 |
| Server VPC `GET /vserver/v2/getZoneList` | 인증에서 거부 |
| Server Classic `GET /server/v2/getRegionList` | 인증에서 거부 |
| VPC `GET /vpc/v2/getVpcList` | 인증에서 거부 |
| SENS `GET /common/v2/projects` | 인증에서 거부 |

> ### ⇒ 메일만의 문제가 아니다. 이 키 쌍으로는 **어떤 NCP API 도** 인증되지 않는다.

이것이 **메일 권한·구독 가설을 없앤다.** 권한은 제품별인데 여섯 제품이 똑같이 막힌다.

> **⚠️ 404 는 인증의 증거가 아니다.** 처음 돌린 판에서 `/vpc/v2/getRegionList` 와
> `/objectstorage/v1/regions` 가 404 를 줘서 "인증 통과" 로 분류했는데, 틀렸다 —
> 그 경로들이 없어서 **라우팅에서 끊긴 것**이고 인증에 닿지도 못했다 (7절 (1) 과 같은 함정).
> 판정 코드에서 `errorCode 300` 을 따로 걸러야 한다.

### 값에는 군더더기가 없다 — 공백 가설도 없앴다

| 확인 | 결과 |
|---|---|
| 키 문자만 지우고 남는 것 | `$` 하나 (ACCESS·SECRET·FROM_ADDRESS 모두) |
| 공백 제거 전후 길이 | ACCESS 28 → 28, SECRET 42 → 42 |
| 돌고 있는 프로세스의 값 | 파일과 sha256 앞 12자 일치 — 재시작은 제대로 먹었다 |

### 키의 종류

| | 값 | 표식 |
|---|---|---|
| 액세스 키 | `ncp_iam_BPAMKR1FbcZLDyL7fDbW` (28자) | `BPAMKR` |
| 시크릿 키 | (42자) `sha256[0:12]=a3d9f3850236` | `BPKMKR` |

액세스 키는 헤더로 평문 전송되는 **식별자**라 가리지 않는다 — 콘솔 목록과 대조하는 데 쓴다.

`ncp_iam_` 다음 6자는 고정 어휘로 보인다 — `BPA*`=Access, `BPK*`=seKret, `*M*`=주계정, `*S*`=서브계정.
그렇다면 **이미 계정(주계정) 인증키**이고, 옛 6절의 "서브 계정 권한·허용 IP" 가설은 애초에 해당이 없다.
단 이 해독은 접두사 모양에 기댄 추론이다 — 콘솔에서 위 액세스 키가 어디 목록에 있는지로 확정한다.

### 서명 계산은 무죄다 — 추정이 아니라 대조했다

5절은 눈으로 본 판단이었다. 프로젝트의 `NcpApiSigner` 를 그대로 컴파일해 `openssl` 과 맞췄다.

```
java    = Wn9p1fzLih/mADT1I4veo7wcoZmTYOdyjuyLt1aZeLQ=
openssl = Wn9p1fzLih/mADT1I4veo7wcoZmTYOdyjuyLt1aZeLQ=
```

`openssl` 쪽은 RFC 표준 시험값(`key` / `The quick brown fox...`)으로 따로 검증했다.
**코드는 맞다. 그리고 `openssl` 로 한 서버 시험은 Java 코드에 대한 유효한 증거다.**

### 콘솔에서 확인한 것 (2026-10-03, 사용자 제공)

제품 쪽은 멀쩡하다. **구독·권한 가설이 여기서도 지워진다.**

| | |
|---|---|
| Mail 서비스 상태 | ● 정상 |
| Mail 서비스 ID | `ncp:mail:kr:377755311848:hanseongge` |
| 월간 최대 이용한도 | 1,000,000 건 (이달 사용 0건) |
| 도메인 `hanseongge.com` | 등록·인증 완료 (2026-09-22) |
| SPF / DKIM | **인증됨** (2026-09-22) |
| DMARC | **미설정** ← 남은 것 (10절) |
| SPF 레코드 값 | `v=spf1 include:email.ncloud.com ~all` |

> **4절을 한 줄 고친다.** "SENS 에는 메일이 없다" 는 **API 문서** 기준으로는 맞지만,
> **콘솔에서는 Mail 이 SENS(Simple & Easy Notification Service) 아래에 있다** —
> SMS · Biz Message · Mail 셋이 한 화면이다. 그래서 "메뉴에서 Cloud Outbound Mailer 가
> 안 보인다" 가 생겼다. 제품이 없어진 것이 아니라 자리가 바뀐 것이다.
> 발송 API 는 그대로 `POST https://mail.apigw.ntruss.com/api/v1/mails` 이고
> **serviceId 를 받지 않는다** (SMS·알림톡만 경로에 serviceId 가 들어간다).

## 7. 옛 7절의 확인 명령 두 개는 쓰지 말 것

둘 다 **틀린 답을 자신 있게 돌려준다.** 이것 때문에 시간을 더 썼을 수 있다.

### (1) 옛 7-3 은 인증을 전혀 보지 않는다

`GET /api/v1/mails` 는 **인증과 무관하게 항상 404** 다. 그 경로에 GET 메서드가 없어서,
게이트웨이가 인증을 보기도 전에 라우팅에서 끊는다. 서명을 제대로 넣어도 똑같다.

```
GET + 가짜 인증 헤더 → 404 {"errorCode":"300","details":"URL not found."}
```

"401 이 아닌 숫자면 인증 통과"라는 판정 기준은 **언제나 통과라고 말한다.**
확인은 반드시 **POST** 로 해야 한다.

### (2) 시크릿을 따옴표 없이 쓰면 범인을 숨긴다

옛 7-1·7-3 은 `openssl dgst -hmac $APP_MAIL_SECRET_KEY` 처럼 따옴표가 없다.
따옴표 없는 전개는 **앞뒤 공백을 셸이 먹어 버린다.** 그래서 지금 가장 의심스러운
"시크릿 끝에 공백 한 칸" 이 섞여 있으면:

| | 서명 |
|---|---|
| Java (공백 포함해서 서명) | `Lq+H4Mdw...` ← NCP 가 거부 |
| `openssl` **따옴표 있음** (공백 포함) | `Lq+H4Mdw...` ← 같다. 정직한 시험 |
| `openssl` **따옴표 없음** (공백이 사라짐) | `Wn9p1fzL...` ← **인증 통과** |

즉 **앱은 계속 실패하는데 시험은 통과한다.** 그러면 "코드가 문제구나" 로 가게 되는데,
코드는 맞다 (6절). 변수는 반드시 `"$VAR"` 로 감싼다.

## 8. 키 교체 (해결됨 — 기록으로 남긴다)

> 실제로는 **원인 1(시크릿 불일치)** 이었다. 아래 진단 절차는 그대로 쓸 만하므로 남긴다.

6절이 남긴 범위다. 셋 다 **콘솔에서 키를 다시 만들면** 닫힌다.

| | 원인 | 왜 아직 남아 있나 |
|---|---|---|
| 1 | **시크릿이 그 액세스 키의 짝이 아니다** | 인증키가 두 벌 있으면 A의 액세스 + B의 시크릿을 섞기 쉽다. 길이(42자)는 정상이라 가려진 `****` 복사는 아니다 |
| 2 | **액세스 키가 비활성·삭제됐다** | 키를 지워도 식별자는 남아 "모르는 키" 와 다른 문구가 날 수 있다 |
| 3 | 키에 **접근 소스(허용 IP)** 제한이 걸려 서버가 빠졌다 | 제품과 무관하게 전부 막히는 것과 들어맞는다. 다만 주계정 인증키라면 해당 없다 (6절) |

`api.env` 는 **2026-09-23 14:56 이후 바뀌지 않았다.** 처음 넣을 때부터 틀린 값이었다는 뜻이다.

### 8-1. 콘솔에서 이 액세스 키를 찾는다

**마이페이지 > 인증키 관리** — https://www.ncloud.com/mypage/manage/authkey

```
ncp_iam_BPAMKR1FbcZLDyL7fDbW
```

- 목록에 **있고 활성** → 원인 1 (시크릿 불일치). 시크릿만 다시 복사해도 될 수 있지만, 아래대로 새로 만드는 쪽이 짧다
- 목록에 **없다** → 원인 2. 다른 계정의 키이거나 지워진 키다
- **Sub Account 쪽**에 있다 → 원인 3 도 봐야 한다 (권한 + API Access Source)

### 8-2. 새로 발급해서 양쪽을 한 번에 복사한다

1. 신규 API 인증키 생성
2. **같은 행**에서 액세스 키 / 시크릿 키(「보기」를 눌러 **펼친 뒤** 전체) 복사
3. `/etc/hanseongge/api.env` 의 `APP_MAIL_ACCESS_KEY`·`APP_MAIL_SECRET_KEY` 교체.
   **값 뒤에 공백·탭이 붙지 않게** (확인은 8-4)
4. `sudo systemctl restart hanseongge-api`
5. 8-3 으로 확인
6. 되면 **옛 키 삭제** (9절 — 유출된 키다)

### 8-3. 확인은 이 한 줄로 (가입 화면으로 하지 말 것)

가입 흐름으로 확인하면 가입 토큰 15분(`OAUTH_SIGNUP_TTL_MINUTES`)이 계속 만료돼 번거롭다.
메일은 나가지 않는다 — 본문이 비어 있어, 인증을 통과하면 **메일 쪽 오류**로 떨어진다.

```bash
sudo bash -c '. /etc/hanseongge/api.env
T=$(($(date +%s)000))
S=$(printf "POST /api/v1/mails\n%s\n%s" "$T" "$APP_MAIL_ACCESS_KEY" \
    | openssl dgst -sha256 -hmac "$APP_MAIL_SECRET_KEY" -binary | base64)
curl -s -w "\nhttp=%{http_code}\n" -X POST https://mail.apigw.ntruss.com/api/v1/mails \
  -H "Content-Type: application/json" \
  -H "x-ncp-apigw-timestamp: $T" \
  -H "x-ncp-iam-access-key: $APP_MAIL_ACCESS_KEY" \
  -H "x-ncp-apigw-signature-v2: $S" -d "{}"'
```

| 돌아온 것 | 뜻 |
|---|---|
| `Invalid authentication information.` | 그대로다. 8-1 로 돌아간다 |
| `This account is not allowed.` | 액세스 키를 아예 못 알아본다. 복사가 잘렸는지 본다 |
| `errorCode 300` / `URL not found.` | **경로를 잘못 쳤다.** 인증과 무관하다 (7절) |
| 그 밖 (400, `senderAddress` 등 메일 오류) | **인증 통과.** 끝났다 |

`-X POST` 를 빼면 안 된다. `GET /api/v1/mails` 는 인증과 무관하게 항상 404 다.

### 8-4. 값에 군더더기가 없는지 (시크릿은 찍히지 않는다)

`file` 로는 꼬리 공백·보이지 않는 문자가 드러나지 않는다 — 줄바꿈 종류만 본다.
키에 쓰이는 문자만 지우고 남는 것을 본다. 깨끗하면 `$` 하나다.

```bash
for V in APP_MAIL_ACCESS_KEY APP_MAIL_SECRET_KEY; do
  printf '%-22s ' "$V"
  sudo grep "^$V=" /etc/hanseongge/api.env | cat -A | sed -E "s/^$V=[A-Za-z0-9_+\/=.@-]*//"
done
```

돌고 있는 프로세스가 같은 값을 들고 있는지 (파일만 고치고 재시작을 잊으면 옛 값이 남는다):

```bash
sudo bash -c '. /etc/hanseongge/api.env
P=$(systemctl show -p MainPID --value hanseongge-api)
echo "파일      $(printf %s "$APP_MAIL_SECRET_KEY" | sha256sum | cut -c1-12)"
echo "프로세스  $(tr "\0" "\n" < /proc/$P/environ | sed -n "s/^APP_MAIL_SECRET_KEY=//p" \
              | sha256sum | cut -c1-12)"'
```

### 8-5. 코드에 넣어 두면 좋을 두 가지 (미적용)

- **키를 읽을 때 잘라내기.** `AppProperties.Mail.isConfigured()` 는 `isBlank()` 만 보므로
  꼬리 공백이 붙은 값이 그대로 통과해 401 로 간다. 이번엔 아니었지만, NCP 키에 공백이
  들어갈 일은 없으니 잘라내는 쪽이 맞다.
- **실패 로그에 NCP `details` 를 그대로.** 지금은 예외 메시지에 묶여 들어가 읽히긴 하지만,
  6절의 사전이 있어야 뜻이 통한다. `details` 를 뽑아 찍고 이 문서를 가리키는 편이 낫다.
