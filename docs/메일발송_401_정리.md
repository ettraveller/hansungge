# 인증 메일이 나가지 않는다 — NCP 401 Authentication Failed

2026-09-28 발생, 2026-10-03 원인 범위 확정. **미해결 — 남은 일은 키 교체다 (8절).** 운영에서 회원가입 중 이메일 인증번호를 받으려 하면 실패한다.

---

## 1. 증상

가입 화면에서 이메일을 넣고 「인증번호 받기」를 누르면:

> 가입하지 못했습니다
> 인증 메일을 보내지 못했습니다. 잠시 후 다시 시도해 주세요.

브라우저 콘솔:

```
api.hanseongge.com/api/v1/auth/email/verification:1  Failed to load resource: 502
```

> ⚠️ **이 502 는 원인을 구분하지 못한다.** 키가 틀려도, 발신 주소가 안 맞아도, 서비스 신청이 안 됐어도
> 전부 같은 `MAIL_SEND_FAILED` 502 로 나온다 (`ErrorCode.java:150`). 화면만 보고 판단하면 안 되고
> **반드시 서버 로그를 봐야 한다.**

참고로 같이 찍히는 `/auth/refresh` 401 은 정상이다 — 로그인하지 않은 상태라서 그렇다. 무관하다.

## 4. 엔드포인트는 살아 있다

콘솔 메뉴에서 Cloud Outbound Mailer 가 안 보여 "제품이 없어진 것 아니냐"는 의심이 있었으나,
**게이트웨이 응답이 아니라고 말한다.**

```bash
curl -s https://mail.apigw.ntruss.com/api/v1/mails
{"error":{"errorCode":"300","message":"Not Found Exception","details":"URL not found."}}

curl -s -X POST https://mail.apigw.ntruss.com/api/v1/mails
{"error":{"errorCode":"200","message":"Authentication Failed",
          "details":"Authentication information are missing."}}   ← 401
```

읽는 법:

- `GET` 은 404 — 그 경로에 GET 메서드가 없을 뿐이다. **제품 유무와 무관하다**
- `POST` 는 401 — **경로가 살아 있고 인증 단계까지 도달한다.** 없어진 주소는 404 를 주지 인증 실패를 주지 않는다
- 헤더 없이 부르면 `missing`, 우리 앱은 `invalid` — 즉 **우리는 헤더를 제대로 보내고 있고 NCP 가 그 값을 거부한다**

공식 문서도 같다:

- SENS API 문서에는 **메일 API 가 없다** (SMS·알림톡·브랜드 메시지 셋뿐)
- Cloud Outbound Mailer API 문서는 살아 있고 `POST /api/v1/mails` 그대로다
- **serviceId 를 받지 않는다.** serviceId 는 SENS 의 SMS·Biz Message 쪽 개념이다

콘솔 메뉴가 개편되어 안 보이는 것과 API 가 없어진 것은 다른 이야기다.

## 5. 우리 구현은 문서와 일치한다 (대조 결과는 6절)

`NcpApiSigner.sign()` — [`NcpApiSigner.java:24-29`](../backend/src/main/java/com/hanseongge/domain/notification/NcpApiSigner.java)

```
StringToSign = "POST /api/v1/mails\n" + timestamp + "\n" + accessKey
signature    = Base64(HmacSHA256(secretKey, StringToSign))
```

헤더 4종 — `Content-Type`, `x-ncp-apigw-timestamp`, `x-ncp-iam-access-key`, `x-ncp-apigw-signature-v2`.
NCP 문서 예시와 같다. **코드를 고칠 이유가 없다.**

## 6. 게이트웨이 오류 문구 사전 — 여기서 범위가 좁혀진다

2026-10-03 추가. 키 없이 **바깥에서** 게이트웨이를 여러 모양으로 찔러 `details` 문구를 모았다.
키가 필요 없는 시험이라 누구나 재현할 수 있다.

```bash
T=$(($(date +%s)000))
curl -s -X POST https://mail.apigw.ntruss.com/api/v1/mails \
  -H "Content-Type: application/json" \
  -H "x-ncp-apigw-timestamp: $T" \
  -H "x-ncp-iam-access-key: ncp_iam_BPASKRaaaaaaaaaaaaaaaa" \
  -H "x-ncp-apigw-signature-v2: AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=" -d '{}'
```

| 보낸 것 | `details` |
|---|---|
| 헤더 3종 중 하나라도 빠짐 (빈 값 포함) | `Authentication information are missing.` |
| 타임스탬프가 과거·미래로 많이 벗어남 | `Expired timestamp.` |
| **모르는 액세스 키** — 포털형·IAM형, 서명이 깨졌든 길이가 다르든 전부 | `This account is not allowed.` |
| 액세스 키 끝에 공백이 붙음 (→ 모르는 키가 된다) | `This account is not allowed.` |
| ← **우리 앱이 받는 것** | `Invalid authentication information.` |

**읽는 법.** 게이트웨이는 **계정을 먼저 찾고, 그 다음에 서명을 검증한다.** 모르는 키로는 서명을
어떻게 보내도 `This account is not allowed.` 에서 멈춘다 — 다섯 가지 모양으로 확인했다.
그런데 우리 앱은 그 벽을 넘어 **다음 단계의 문구**를 받는다.

> ### ⇒ 액세스 키는 NCP 가 알아본다. 떨어지는 곳은 **서명 검증**이다.
>
> 즉 **시크릿 키가 그 액세스 키의 짝이 아니다** (또는 값에 군더더기가 붙어 있다).

이것이 2절의 로그를 처음으로 한 가지 원인으로 좁힌다.

### 서명 계산은 무죄다 — 추정이 아니라 대조했다

5절은 "문서와 형식이 같다"는 눈으로 본 판단이었다. 실제로 맞춰 보았다 —
프로젝트의 `NcpApiSigner` 를 그대로 컴파일해 `openssl` 과 같은 입력을 주었다.

```
java    = Wn9p1fzLih/mADT1I4veo7wcoZmTYOdyjuyLt1aZeLQ=
openssl = Wn9p1fzLih/mADT1I4veo7wcoZmTYOdyjuyLt1aZeLQ=
```

`openssl` 쪽은 RFC 표준 시험값(`key` / `The quick brown fox...`)으로 따로 검증했다.
**두 결론: 코드는 맞다. 그리고 `openssl` 로 한 서버 시험은 Java 코드에 대한 유효한 증거다.**

## 7. 옛 7절의 확인 명령 두 개는 쓰지 말 것

둘 다 **틀린 답을 자신 있게 돌려준다.** 이것 때문에 시간을 더 썼을 수 있다.

### (1) 옛 7-3 은 인증을 전혀 보지 않는다

`GET /api/v1/mails` 는 **인증과 무관하게 항상 404** 다. 그 경로에 GET 메서드가 없어서,
게이트웨이가 인증을 보기도 전에 라우팅에서 끊는다. 서명을 제대로 넣어도 똑같다.

```
GET + 가짜 인증 헤더 → 404 {"errorCode":"300","details":"URL not found."}
```

"401 이 아닌 숫자면 인증 통과"라는 판정 기준은 **언제나 통과라고 말한다.**
확인은 반드시 **POST** 로 해야 한다.

### (2) 시크릿을 따옴표 없이 쓰면 범인을 숨긴다

옛 7-1·7-3 은 `openssl dgst -hmac $APP_MAIL_SECRET_KEY` 처럼 따옴표가 없다.
따옴표 없는 전개는 **앞뒤 공백을 셸이 먹어 버린다.** 그래서 지금 가장 의심스러운
"시크릿 끝에 공백 한 칸" 이 섞여 있으면:

| | 서명 |
|---|---|
| Java (공백 포함해서 서명) | `Lq+H4Mdw...` ← NCP 가 거부 |
| `openssl` **따옴표 있음** (공백 포함) | `Lq+H4Mdw...` ← 같다. 정직한 시험 |
| `openssl` **따옴표 없음** (공백이 사라짐) | `Wn9p1fzL...` ← **인증 통과** |

즉 **앱은 계속 실패하는데 시험은 통과한다.** 그러면 "코드가 문제구나" 로 가게 되는데,
코드는 맞다 (6절). 변수는 반드시 `"$VAR"` 로 감싼다.

## 8. 다음에 할 것

### 8-1. 값을 눈으로 확인한다 (시크릿은 찍지 않는다)

`file` 로는 **꼬리 공백·보이지 않는 문자**가 드러나지 않는다 — 줄바꿈 종류만 본다.
키에 쓰이는 문자만 지우고 남는 것을 본다. 깨끗하면 `$` 하나만 나와야 한다.

```bash
sudo grep '^APP_MAIL_SECRET_KEY=' /etc/hanseongge/api.env \
  | cat -A | sed 's/^APP_MAIL_SECRET_KEY=[A-Za-z0-9_+/=-]*//'
sudo grep '^APP_MAIL_ACCESS_KEY=' /etc/hanseongge/api.env \
  | cat -A | sed 's/^APP_MAIL_ACCESS_KEY=[A-Za-z0-9_+/=-]*//'
```

길이와 앞머리만 (시크릿은 해시 앞 12자만):

```bash
sudo bash -c '. /etc/hanseongge/api.env
printf "access len=%s head=%s\n" "${#APP_MAIL_ACCESS_KEY}" "${APP_MAIL_ACCESS_KEY:0:14}"
printf "secret len=%s sha=%s\n"  "${#APP_MAIL_SECRET_KEY}" \
  "$(printf %s "$APP_MAIL_SECRET_KEY" | sha256sum | cut -c1-12)"'
```

**돌고 있는 프로세스가 같은 값을 들고 있는지**도 본다. 파일을 고쳐도 재시작을 안 하면 옛 값이 남는다.

```bash
sudo tr '\0' '\n' < /proc/$(systemctl show -p MainPID --value hanseongge-api)/environ \
  | grep '^APP_MAIL_' | sed 's/\(SECRET_KEY=\).*/\1<생략>/'
```

### 8-2. 결정적인 한 방 — POST 로, 따옴표를 붙여서

메일은 나가지 않는다 (본문이 비어 있어, 인증을 통과하면 메일 쪽 오류로 떨어진다).

```bash
sudo bash -c '. /etc/hanseongge/api.env
T=$(($(date +%s)000))
S=$(printf "POST /api/v1/mails\n%s\n%s" "$T" "$APP_MAIL_ACCESS_KEY" \
    | openssl dgst -sha256 -hmac "$APP_MAIL_SECRET_KEY" -binary | base64)
curl -s -w "\nhttp=%{http_code}\n" -X POST https://mail.apigw.ntruss.com/api/v1/mails \
  -H "Content-Type: application/json" \
  -H "x-ncp-apigw-timestamp: $T" \
  -H "x-ncp-iam-access-key: $APP_MAIL_ACCESS_KEY" \
  -H "x-ncp-apigw-signature-v2: $S" -d "{}"'
```

| 돌아온 `details` | 뜻 | 할 일 |
|---|---|---|
| `Invalid authentication information.` | 서명 불일치. **시크릿이 짝이 아니다** | 8-3 |
| `This account is not allowed.` | 액세스 키를 못 알아본다 | 8-3 (둘 다 새로) |
| 그 밖 (400, `senderAddress` 등 메일 오류) | **인증 통과.** 그러면 범인이 코드로 바뀐다 | 6절 대조를 서버에서 다시 |

### 8-3. 두 쪽을 같은 줄에서 새로 복사한다

**마이페이지 > 인증키 관리**(https://www.ncloud.com/mypage/manage/authkey) 에서 신규 발급.
계정 인증키는 권한·IP 제한을 받지 않는다.

1. 신규 API 인증키 생성
2. **같은 행**에서 액세스 키 / 시크릿 키(「보기」를 눌러 **펼친 뒤** 전체) 복사 —
   가려진 `****` 를 복사하면 지금과 똑같은 증상이 난다
3. `/etc/hanseongge/api.env` 갱신. **값 뒤에 공백·탭이 붙지 않게** (8-1 로 확인)
4. `sudo systemctl restart hanseongge-api`
5. 8-2 로 확인
6. 되면 **옛 키 삭제** (9절)

### 8-4. 남아 있는 단 하나의 가정

6절은 "`Invalid authentication information.` 은 서명 검증 실패뿐"이라는 전제 위에 선다.
바깥에서는 **인식되는 키**를 만들 수 없어 그 한 갈래만 시험하지 못했다 —
서브 계정 키가 계정은 찾았는데 **권한·API Access Source(허용 IP)** 에서 걸릴 때도
같은 문구가 날 가능성이 남는다.

**8-3 으로 계정 인증키로 갈아도 그대로면**, 그때 거기를 본다 (옛 6절 (나) 가설):

| 확인할 곳 | |
|---|---|
| 서비스 권한(정책) | Sub Account > 해당 계정 > 권한에 메일 발송 권한 |
| API Access Source | 서버 공인 IP 등록 여부 (`curl -s ifconfig.me`) |

### 8-5. 코드에 넣어 두면 좋을 두 가지 (미적용)

- **키를 읽을 때 잘라내기.** `AppProperties.Mail.isConfigured()` 는 `isBlank()` 만 보므로
  꼬리 공백이 붙은 값이 그대로 통과해 401 로 간다. NCP 키에 공백이 들어갈 일은 없으니
  잘라내는 쪽이 맞다. 보이지 않는 오타 하나가 반나절이 되는 것을 막는다.
- **실패 로그에 NCP `details` 를 그대로.** 지금은 예외 메시지에 묶여 들어가 읽히긴 하지만,
  6절의 표가 있어야 뜻이 통한다. `details` 를 뽑아 찍고 이 문서를 가리키는 편이 낫다.
