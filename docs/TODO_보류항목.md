### B-5 참고 — 한국금거래소(koreagoldx.co.kr) 시세 페이지 구조 분석 (2026-09-08)

경쟁사가 시세를 <b>어떻게 나눠 보여주는지</b> 확인했다. 세 페이지가 데이터 출처부터
다르고, 그 구분이 우리 3층 구조와 정확히 대응한다.

| 페이지 | 출처 | 갱신 | 우리 대응 |
|---|---|---|---|
| `/price/gold` | 자체 DB, 관리자 고시 | 하루 여러 번 | **이미 있음** — 시세관리 + `/price` |
| `/price/global` | 자체 수집(국제가+환율) | <b>1분</b> | 데이터 공급자 계약 선행 (B-1·B-4) |
| `/price/trading-view` | TradingView 위젯 임베드 | 실시간(외부) | 스크립트 한 줄이면 가능 |

#### 고시가는 국제시세를 자동으로 따라가지 않는다

같은 시각으로 맞춰 비교했다.

```
고시시각              살때      팔때     같은시각 국제(원/돈)   차이     팔때/국제
2026-09-08 13:07:46  845,000  720,000       719,151        +849      1.0012
2026-09-08 09:44:01  842,000  717,000       715,829      +1,172      1.0016
```

매입가가 국제시세에 <b>거의 붙어 있지만 비율이 고정이 아니다</b>(1.0012 vs 1.0016).
자동 계산이면 이 값이 같아야 한다. 그리고

- 고시가는 예외 없이 <b>천원 단위</b>다. 국제시세는 소수점까지 나온다
- 살 때와 팔 때의 간격이 124~128천원으로 흔들린다. 자동 파생이면 고정이어야 한다

즉 <b>「국제시세 참고 → 사람이 마진 판단 → 고시」</b>이지 기계적 연동이 아니다.
우리 설계의 L1(원본) / L2(정책) / L3(최종) 분리와 같은 구조이고, 그래서
`/price/global` 이 없어도 `/price/gold` 는 성립한다 — 지금 우리 상태가 그것이다.

#### ★ 순금 → 18K/14K 는 기계적으로 파생된다 (A-7 실사례)

여기엔 판단이 없다. 날짜를 바꿔도 정확히 맞는다.

```
845,000 × 0.735 = 621,075  = 18K 살 때
845,000 × 0.57  = 481,650  = 14K 살 때
720,000 × 0.735 = 529,200  = 18K 팔 때   ← 매입가도 같은 비율
```

<b>18K = 0.735, 14K = 0.57, 매입·판매 양쪽 동일.</b> 순도만 보면 18K는 0.75,
14K는 0.5833 인데 그보다 낮게 잡았다 — 세공 손실분을 반영한 것으로 보인다.

이 값을 그대로 쓸지는 <b>발주처가 정할 일</b>이다(A-7). 다만 "업계가 실제로 어떤
값을 쓰는가"의 근거가 없어 미뤄 두었던 항목이라, 물어볼 때 이 숫자를 제시할 수 있다.

종가이므로, 저쪽은 <b>다른 공급자</b>를 쓴다 — 유료 상용 피드일 가능성이 높다.
B-4(30분 갱신 공급자)를 판단할 때 참고가 된다.

```html

<script>
```

TradingView 에 직접 붙으므로 <b>계약도 수집도 필요 없다.</b> 대신 우리 고시가와
값이 다를 수 있어, 저쪽은 페이지에 그 사실을 적어 두었다.

"왜 고시가와 다르냐"고 묻는 것이 기본값이다.

구현을 새로 추가하는 편이 낫다 — 두 소스는 응답 형태도 약관도 다르다.

### B-4 상세 — 30분 간격 시세 공급자 (2026-09-06)

발주자가 <b>30분 간격 갱신</b>을 요구했다. 스케줄러·3층 구조·Provider 인터페이스는
모두 만들어져 있고, 결정이 필요한 것은 L1 에 무엇을 꽂느냐 하나다.

| 소스 | 갱신 주기 | 무료 한도 | 30분 가능 |
|---|---|---|---|
| KRX Open API | 일 1회(종가) | 무료 | ❌ 같은 값 반복 |
| 한국은행 ECOS | 일 1회 | 무료 | ❌ |
| GoldAPI·metals.dev 류 | 실시간 | 월 100회 | ❌ 370회 필요 |
| Yahoo Finance(비공식) | 실시간 | 무제한 | ⚠️ 상업적 이용 ToS 위반 |

국내 금 소매시세는 원래 실시간으로 정해지지 않는다. 실시간으로 움직이는 것은
국제 금값(XAU/USD)과 환율이고, 국내 소매가는 거기에 업체 마진을 얹어 <b>사람이
정하는 값</b>이다. 그래서 어떤 공급자를 쓰든 L2 정책 계층은 그대로 필요하다.

<b>선택지</b>

- <b>A. 유료 API (월 0~30)</b> — 라이선스가 명확하고 주기 제약이 없다. 가격은 이
  사이트에서 가장 비싼 실패 지점이라, 그 위험을 월 3만원으로 없앨 수 있으면 싸다.
- <b>B. KRX 일 1회 + 수동 조정</b> — 무료·합법. 장중 변동은 관리자가 /admin/prices
  에서 반영한다. 실제 금은방 운영 방식에 가장 가깝다.
- <b>C. 무료 API 여러 개 조합</b> — 월 100회짜리 3~4개로 370회를 채운다. 한 곳이
  정책을 바꾸면 시세가 멈춘다. 설계 원칙 P6 에 반한다 — <b>권하지 않는다.</b>

<b>스크래핑은 검토 대상이 아니다.</b> kaggold 의 index.grp_ajax2.php 는 경쟁사 자산이고,
상대가 HTML 한 줄만 바꿔도 가격이 깨진다.

### B-1 상세 — KRX 시세 API 조사 결과 (2026-08-30)

후보가 둘이고, **둘 다 무료·자동승인이며 과거 데이터를 준다.**

| | 공공데이터포털 <br>금융위원회_일반상품시세정보 | KRX 공식 <br>Data Marketplace Open API |
|---|---|---|
| 주소 | [data.go.kr/data/15094805](https://www.data.go.kr/data/15094805/openapi.do) | [openapi.krx.co.kr](https://openapi.krx.co.kr/) |
| 해당 오퍼레이션 | `getGoldPriceInfo` (금시세) | 금시장 일별매매정보 |
| **과거 데이터** | 제공 (형제 API 와 같은 `beginBasDt`/`endBasDt` 패턴. 정확한 파라미터는 활용가이드 `.docx` 확인 필요) | **2014-03-24 데이터부터 제공** — 12년치 |
| 갱신주기 | **일 1회** | **일 1회** (일별매매정보) |
| 승인 | 개발·운영 모두 자동승인 | 인증키 신청 후 보통 1일 내 승인 |
| 호출 한도 | 개발계정 10,000건/일 | 인증키당 10,000건/일 |
| 비용 | 무료 | 무료 |
| 상업적 이용 | **미확인** | **미확인** |

**과거 데이터 조회는 가능합니다.** 특히 KRX 공식 API 는 2014년부터 일별로 다 있어서, 최초 1회 배치로 전체 이력을 끌어와 채우면 그래프가 바로 완성됩니다.

#### 짚어야 할 것 세 가지

**① 30분 간격 적재는 의미가 없습니다.**
두 API 모두 갱신주기가 **일 1회(종가)** 입니다. 30분마다 부르면 같은 값을 48번 받아
`market_price_raw` 에 중복 원본만 쌓입니다(V8 의 `ux_mpr_dedup` 이 막아 주긴 합니다).
**일 1회 배치(장 마감 후)로 충분하고, 그게 이 API 의 설계 주기입니다.**
장중 실시간 시세가 필요하면 그건 이 API 가 아니라 유료 벤더 영역입니다(D 항목).

**② 상업적 이용 조항만 남았습니다.**
이것이 B-1 의 진짜 잔여 리스크입니다. 두 API 모두 무료지만, 받은 데이터를 상업
사이트의 판매가 산정 근거로 쓰는 것이 약관상 허용되는지는 각 이용약관을 읽어야
합니다. KRX 는 `krxdata@krx.co.kr` 로 문의 가능합니다.
**확인 전에는 `KrxMarketPriceProvider` 를 켜지 않습니다** — 켜는 순간 위반이 될 수
있고, 그래서 지금 껍데기로 두었습니다.

**③ 경쟁사(kaggold.com) 데이터를 긁어오는 방안은 권하지 않습니다.**
그 사이트가 `index.grp_ajax2.php` 로 2021년부터의 일별 시세를 통째로 내려주는 것은
맞습니다. 다만 그것은 **공개 API 가 아니라 자사 화면용 내부 엔드포인트**이고, 그
데이터셋 자체가 경쟁사가 비용을 들여 축적한 자산입니다. 우리 판매가의 근거로 쓰면
출처를 밝힐 수도 없습니다. **KRX 가 2014년부터 공식으로 주므로 그럴 이유도 없습니다.**

#### 실시간 시세는 되는가 (2026-08-30 조사)

**무료 공식 API 로는 안 된다.** 공공데이터포털·KRX Open API 모두 일 1회 종가다.
실시간이 되는 경로는 셋이고, 각각 조건이 붙는다.

| 경로 | 무엇 | 제약 |
|---|---|---|
| **증권사 REST API** <br>(키움 2025-09-19 개시, 한국투자 등) | KRX 금시장 **실시간 시세 + 주문**. 원화 기준이라 환율 불필요 | **증권 계좌 필요.** 원래 목적이 자동매매고 시세는 부산물. <br>**대외 재배포(공개 사이트 게시) 조건 확인 필요** — 내가 보는 것과 고객에게 보여주는 것은 다른 문제다 |
| **국제시세 API** <br>(metals.dev, GoldAPI 등) | XAU/USD 실시간. 월 $20 수준 | **환율 API 추가 필요.** 국제시세는 국내 소매가와 다른 지표라 참고 그래프용이지 판매가 근거로는 안 맞는다 |
| **KRX 정보데이터시스템 크롤링** | 장중 데이터 있음 | 약관 저촉 위험 — B-1 에서 이미 보류한 방안 |

#### 결론: 지금은 실시간이 필요하지 않다

**kaggold(업계 1군)도 영업일 1회 갱신이다.** 2026-08-30(일)에 사이트에 찍힌 날짜가
2026.08.29 인 것을 확인했다. 실시간을 쓰지 않는 데 이유가 있다.

실시간을 붙이면 생기는 문제:

- 고객이 **그 가격으로 주문 가능하다고 기대**한다. 실제 판매가는 스프레드 + 공임이라 다르다
- 장바구니에 담긴 가격이 계속 어긋난다. `priceChanged` 처리는 되어 있지만
  "시세가 변경되었습니다"가 30분마다 뜨면 오히려 신뢰가 떨어진다
- 급등락 때 **역마진**이 난다. 그래서 승인 대기(`market_price_pending`)를 둔 것이다
- 증권 계좌 + 재배포 조건 + 유지보수가 따라붙는다

**이 사이트가 파는 것은 실물 금이지 금 시세가 아니다.** 시세는 "우리 가격이 시장을
따라간다"를 보여주는 신뢰 장치이고, 그 목적에는 일 1회 종가로 충분하다.

실시간이 실제로 필요해지는 시점은 **온라인 매입 접수를 시작할 때**다(D 항목). 그때
증권사 API 를 검토한다.

#### 권장 순서

1. KRX Open API 인증키 신청 → 금시장 일별매매정보 서비스 신청 (승인 ~1일)
2. **이용약관의 상업적 이용 조항 확인** — 불명확하면 `krxdata@krx.co.kr` 문의
3. 허용되면 → 최초 1회 전체 이력 백필 배치 + 일 1회 종가 수집으로 전환
4. 허용되지 않으면 → 현행 유지(관리자 수동 고시 주력). 이력은 고시가 쌓이며 생긴다

#### 시세와 판매가의 관계 (설계 확인)

조사 중 확인된 업계 관행이 현재 설계와 일치합니다.

- kaggold 의 순금 3.75g 은 **살 때 868,000 / 팔 때 726,000 으로 스프레드가 16.4%** 입니다.
  마진은 시세가 아니라 **매수·매도 스프레드**에서 나옵니다 → 우리 `market_price_policies`
  가 metal × **side** 로 나뉘어 있는 이유가 이것입니다. 이미 맞습니다
- 18K·14K 는 "내가 살 때"가 없고 **"제품시세적용"** 입니다. 세공품은 공임이 제품마다
  달라 자동 계산을 포기하고 개별 가격을 매깁니다 → 우리도 세공품은 `FIXED`/`MANUAL`
  로 두고 **골드바만 시세 연동**하면 됩니다. `price_type` 4종이 이미 그 구조입니다
- 자동 계산은 제안까지만 하고 최종 발행은 사람이 승인 → 우리 `market_price_pending`
  (변동률 임계 초과 시 승인 대기)이 그 역할입니다

즉 **A-7(금속별 파생 비율·마진 정책)만 확정되면** 현재 구조 그대로 운영 가능합니다.

### C-5. STEP 6 에서 내린 설계 결정

| 항목 | 결정 | 사유 |
|---|---|---|
| **보류(pending)를 예외로 던지지 않음** | `PriceApplyResult.applied=false` + HTTP 200 | 변동률 초과 보류는 오류가 아니라 **설계된 정상 경로**다. 예외로 던지면 관리자 화면에 "승인이 필요합니다"가 아니라 "오류가 발생했습니다"가 뜬다 |
| **마감 UPDATE 를 명시적으로 flush** | 기존 행 `close()` 후 `saveAndFlush`, 그다음 신규 INSERT | JPA 는 INSERT 를 UPDATE보다 앞세운다. flush 가 없으면 신규 행(`effective_to IS NULL`)이 먼저 들어가 부분 UNIQUE 인덱스 `ux_mpe_current` 를 위반한다 |
| **advisory lock (metal×side)** | `pg_advisory_xact_lock(hashtext(key))` | 최초 발행 시에는 **잠글 행 자체가 없어** 행 잠금으로는 동시성을 막을 수 없다. 행이 아니라 키를 잠근다. 부분 UNIQUE 인덱스가 최종 안전망이라 락이 없어도 데이터는 깨지지 않고 예외로 실패한다 |
| **승인 시 변동률 재검사 안 함** | 보류 당시 `calc_price` 를 그대로 발행 | 임계값 초과를 알고도 승인한 것이라 다시 막으면 승인이 무의미하다. 재계산도 하지 않는다 — 승인 시점에 정책이 바뀌어 있으면 화면에서 본 값과 다른 값이 발행된다 |
| **MANUAL 인데 `manual_price` 가 NULL** | 원본을 그대로 최종가로 적용 + 조합당 1회 WARN | V2 가 전 금속×side 를 `MANUAL`+NULL 로 시드한다. 예외로 처리하면 **수동 고시(주력 경로)가 첫 시도부터 실패**한다. 지정가가 없다는 것은 오버라이드할 것이 없다는 뜻이다 |
| **수집 실패는 원본을 만들지 않음** | `market_price_fetch_logs` 에만 기록 | 원본이 없으면 발행도 없고, 발행이 없으면 기존 시세가 유지된다. "실패가 가격을 0원으로 만들지 않는다"의 구조적 근거 |
| **재시도 대상 구분** | HTTP_ERROR / TIMEOUT / EXCEPTION 만 3회, PARSE_ERROR·INVALID_VALUE 는 1회 | 값이 이상하거나 파싱이 안 되는 것은 다시 불러도 똑같다. 로그만 3배로 늘고 API 쿼터를 태운다 |
| **쓰기를 별도 빈으로 분리** | `MarketPriceCollectionWriter` | `REQUIRES_NEW` 를 같은 클래스 안에 두면 자기 호출이라 **프록시를 타지 않아 어노테이션이 조용히 무시된다.** 장애 전까지 드러나지 않는 결함이라 빈을 나눠 구조적으로 막았다 |
| **감사로그를 이벤트 리스너가 아니라 서비스에서** | 리스너는 캐시 무효화만 | §12.7 은 리스너에서 감사도 기록하도록 그렸으나, 행위자·사유·보류 여부 맥락이 서비스에 있다. **보류로 끝난 경우는 이벤트 자체가 발행되지 않아** 리스너에서는 기록할 수 없다 |
| **스케줄러 cron 을 DB 에서 매 실행 재조회** | `SchedulingConfigurer` + 동적 `CronTrigger` | `@Scheduled(cron=상수)` 는 주기 변경이 재배포다. 잘못된 cron 이면 기본값으로 되돌리고 WARN — cron 오타 하나로 수집이 영영 멈추는 것이 더 큰 사고다 |
| **`isDeclaredByAdmin()` 이 `created_by` 를 봄** | `source.getCode()` 대신 | `source` 는 지연로딩이라 트랜잭션 밖에서 부르면 `LazyInitializationException` 이다. 판정 하나 때문에 응답 전체가 500 이 되는 함정 (통합테스트가 실제로 잡았다) |
| **공개 API 는 노후 시세를 내보내지 않음** | 관리자 API 는 노후 값도 노출 | 관리자는 "무엇이 언제부터 낡았는지"를 봐야 하고, 고객은 화면에 뜬 가격으로 주문하려 한다 |

### C-6. STEP 7 에서 내린 설계 결정

| 항목 | 결정 | 사유 |
|---|---|---|
| **부가세 미확정(A-1)** | 예외 대신 임시 `NONE`(면세) + WARN 1회 | A-2 반올림과 같은 처리다. 세 후보 중 **최종 금액을 바꾸지 않는 유일한 값**이라 골랐다 — `EXCLUDED` 면 구성요소 합계보다 10% 비싼 가격이, `INCLUDED` 면 면세 상품에 세액이 표시된다 |
| **SIMPLE 도 구성요소로 정규화** | `price_type` 컬럼 → `ComponentLine` 목록으로 변환 후 계산 | 개발계획 §13.1. 주얼리용 `product_price_components`(D-1)가 들어와도 **불러오는 곳만 바뀌고 계산·Snapshot·테스트는 그대로**다 |
| **구성요소 합계 = 소계 (불변식)** | 각 줄을 전(錢) 단위 `Money` 로 확정한 뒤 더한다 | 개발계획 §13.5 는 `MathContext.DECIMAL64` 누적을 그렸으나, 그러면 줄 합계와 소계가 1원씩 어긋날 수 있다. **주문 명세서의 항목 합이 청구액과 달라지는 것**이 더 큰 문제라 줄 단위 확정을 택했다 (DB 는 어차피 `NUMERIC(15,2)`) |
| **반올림은 마지막 1회** | 소계·세액에는 적용하지 않고 합계에만 | 단계마다 반올림하면 구성요소 합계와 최종가가 어긋난다. `roundingDelta` 로 조정액을 노출해 검증 가능하게 했다 |
| **배수를 별도 줄로 분리** | `MARKET_MULTIPLIER` 를 `METAL_BASE` + `MARGIN(×배수-1)` 로 | METAL_BASE 에 배수를 곱해 넣으면 상세페이지에 "210,000 × 3.75 = 905,625" 처럼 **계산이 맞지 않는 줄**이 표시된다 |
| **시세 없음/노후는 예외 아님** | `PriceStatus.INQUIRY_ONLY` 반환, 금액 필드는 `null` | 예외로 던지면 목록에 시세 없는 상품 하나가 섞였을 때 **목록 전체가 500** 이 된다. 0 을 돌려주지 않는 이유는 화면에 "0원"으로 그려지기 때문 |
| **관리자 미리보기는 캐시·노출검사 제외** | HIDDEN 상품도 계산, 캐시 미사용 | 없으면 운영자가 가격 확인을 위해 **일단 공개했다가 되돌리는** 절차를 쓰게 된다 |
| **옵션 추가공임은 MARKET_PLUS 만** | 다른 타입이면 무시하되 WARN | 설계서 §7.1 그대로다. 조용히 무시하면 "왜 반영이 안 되지"로 시간이 샌다 |
| **대표가는 최저가 옵션** | 목록 화면의 "○○원~" | 옵션 미지정 조회에서는 재고를 보지 않는다 — 어떤 옵션이든 하나라도 살 수 있으면 목록에서 "품절"로 표시하면 안 된다 |
| **`price_calculation_logs` 미구현** | STEP 13(주문)로 미룸 | §13.7 은 `ORDER` / `ADMIN_PREVIEW` 전건 저장을 요구한다. 주문이 없는 지금은 `ADMIN_PREVIEW` 뿐이라 감사 가치가 낮고, 테이블 신설(마이그레이션)을 정당화하지 못한다 |

### C-7. STEP 8 에서 내린 설계 결정

| 항목 | 결정 | 사유 |
|---|---|---|
| **상품 DELETE 없음** | 판매 종료는 `status=DISCONTINUED` | 상품을 지우면 그 상품을 담은 **과거 주문의 상품 정보가 사라진다**. 관리자 계정과 같은 원칙 |
| **등록 직후 `HIDDEN`** | 관리자가 확인 후 `PATCH /{id}/status` 로 판매 시작 | 등록 시점에는 재고·이미지가 없고 시세 연동이면 가격도 미확인이다. 그대로 노출되면 고객이 **재고 없는 상품을 주문**하거나 잘못된 가격을 본다 |
| **기본 옵션 자동 생성 (D-7)** | 옵션 없이 등록하면 서버가 1개를 만든다. 마지막 활성 옵션은 비활성화 불가 | "옵션 없는 상품" 개념을 없애면 재고 소스가 `product_options.stock` 한 곳뿐이고, 주문·취소·환불의 재고 경로가 분기 없이 단일해진다 (개발계획 §9.3). **단 `is_default` 컬럼과 부분 UNIQUE 인덱스는 V8 대기** — 지금은 응용 계층 방어다 |
| **`ProductPricing` 값 객체** | `price_type` 별 필수값을 한 곳에서 검증 | 흩어 두면 서비스·컨트롤러·엔티티 중 한 곳만 빠뜨려도 통과한다. DB 제약(`chk_price_type_fields`)만 믿으면 관리자 입력 오류가 **500 으로 나간다** |
| **재고 조정은 절대 수량** | 증감이 아니라 "조정 후 수량" | 실사는 "세어 보니 7개였다"이지 "3개 줄여라"가 아니다. 증감이면 요청이 중복 도착할 때 재고가 두 번 깎인다 |
| **재고 조정과 주문 차감 분리** | `adjustStock` ≠ (STEP 13) `decreaseStock` | 같은 메서드면 실사 입력이 주문 차감과 경합하고, 감사로그에서도 둘을 구분할 수 없다 |
| **노출 조건을 서버가 강제** | 공개 검색은 `condition.forPublic()` 으로 `status`·`active` 를 덮어쓴다 | 클라이언트가 끌 수 있으면 **파라미터 하나로 숨김 상품을 열람**할 수 있다 |
| **숨김 상품 상세는 403 이 아니라 404** | 존재 자체를 알리지 않는다 | 403 이면 "여기 뭔가 있다"가 새어 나가 상품 ID 를 훑어 미공개 상품 목록을 만들 수 있다 |
| **공개 응답에 재고 수량 없음** | `inStock`(불리언)만 노출 | 정확한 재고는 영업 정보다. 고객이 알아야 할 것은 "살 수 있는가" 뿐 |
| **가격 산출 실패가 목록을 죽이지 않음** | 상품별로 잡아 "시세문의"로 그리고 WARN | 상품 하나의 설정 오류(중량 누락 등)로 **목록 전체가 500** 이 되면 안 된다 |
| **카테고리 순환 참조 차단** | 자기 자신·하위를 부모로 지정 불가, 깊이 32 가드 | 트리가 고리가 되는 순간 카테고리를 순회하는 모든 코드가 **무한 루프**에 빠진다. 화면이 멎을 때까지 아무도 눈치채지 못한다 |
| **사용 중 카테고리 삭제 차단** | 상품·하위가 있으면 409, `active=false` 로 숨김 | 지우면 그 상품들이 **존재하지 않는 분류**를 가리키고 목록에서 조용히 사라진다 |
| **이미지는 목록 통째 교체** | 개별 추가·삭제 대신 `PUT /{id}/images` | 순서가 의미를 갖는 목록이라, 개별 조작은 여러 요청으로 나뉘며 중간 상태가 화면에 노출된다 |

### E-1. 소셜 로그인 3사 (TODO A-4)

세 곳 모두 공통으로 **콜백 주소가 글자 하나까지 같아야 한다.** 다르면 로그인 직전에
제공자가 거부하고, 원인 메시지가 친절하지 않아 찾는 데 시간이 걸린다.

```
개발  http://localhost:3000/auth/callback/{google|naver|kakao}
운영  https://hanseongge.com/auth/callback/{google|naver|kakao}
```

받은 값은 `backend/.env` (운영은 `/etc/hanseongge/api.env`)에 넣는다.
**값을 채운 제공자만 로그인 화면에 버튼으로 나온다** — 검수가 안 끝난 곳은 비워 두면 된다.

#### 구글 — 가장 쉽다. 사업자 서류 없이 오늘 된다

1. [Google Cloud Console](https://console.cloud.google.com) → 프로젝트 생성
2. **API 및 서비스 → OAuth 동의 화면**
   - User Type: **외부**
   - 앱 이름 `한성금거래소`, 지원 이메일, 개발자 연락처
   - 범위(Scopes): `userinfo.email`, `userinfo.profile`
   - **테스트 사용자**에 테스트할 지메일 주소 추가 (게시 전에는 등록된 계정만 로그인된다)
3. **사용자 인증 정보 → OAuth 클라이언트 ID → 웹 애플리케이션**
   - 승인된 리디렉션 URI 에 위 콜백 주소 입력
4. 발급값 → `OAUTH_GOOGLE_CLIENT_ID`, `OAUTH_GOOGLE_CLIENT_SECRET`
5. 실서비스 공개 시 **앱 게시(검증)** 필요 — 개인정보처리방침 URL 요구 (A-6 연동)

#### 네이버 — 검수 있음. 사업자 정보 필요

1. [네이버 개발자센터](https://developers.naver.com) → 애플리케이션 등록
2. 사용 API: **네이버 로그인** → 제공 정보에 **이메일·이름** 체크
   - 필수로 받을수록 검수가 까다로워진다. 꼭 필요한 것만 체크할 것
3. 환경: PC 웹 → 서비스 URL `https://hanseongge.com`, 콜백 URL 위와 동일
4. 발급값 → `OAUTH_NAVER_CLIENT_ID`, `OAUTH_NAVER_CLIENT_SECRET`
5. **검수 신청** — 개인정보처리방침 URL, 서비스 설명, 로그인 화면 캡처 요구
   - 소요: 수일 ~ 2주. 반려되면 사유 고쳐 재신청
6. 검수 전에도 **개발자 본인 계정으로는** 로그인 테스트가 된다

> ⚠️ 네이버 응답은 다른 두 곳과 달리 실제 값이 `response` 안에 한 겹 더 들어 있고
> `resultcode` 로 성공 여부를 준다. 이 차이는 `NaverOAuthProvider` 가 이미 흡수한다.

#### 카카오 — 검수 있음. 이메일이 없을 수 있다

### E-2. PostgreSQL — 앱 서버에 직접 (2026-09-23 이후)

**`provision.sh` 5~7절이 전부 한다.** 설치·설정·역할/DB 생성·백업 크론까지. 사람이 할 일은
**DB 비밀번호를 정해 양쪽에 같은 값을 넣는 것** 하나뿐이다.

```bash
sudo -u postgres psql -c "ALTER ROLE hanseongge PASSWORD '<정한 값>'"
vi /etc/hanseongge/api.env     # DB_PASSWORD 에 같은 값
```

```
DB_URL=jdbc:postgresql://localhost:5432/hanseongge
DB_USERNAME=hanseongge
DB_PASSWORD=<정한 값>
DB_POOL_SIZE=20
```

스크립트가 지키는 것 — 바꿀 때 그대로 둘 것:

1. **버전 16**, PGDG 저장소. 우분투 기본 저장소는 배포판 수명 동안 한 버전에 묶여 마이너 보안
   패치가 늦다. 하위 버전은 Flyway 가 V1 부터 실패한다 (JSONB·plpgsql 트리거·부분 UNIQUE 인덱스)
2. **DB 소유자를 `hanseongge` 로.** PostgreSQL 15+ 는 `public` 스키마의 CREATE 권한을 PUBLIC 에서
   회수해서, `GRANT ALL PRIVILEGES ON DATABASE` 만으로는 Flyway 가 V1 에서
   `permission denied for schema public` 로 죽는다
3. **`listen_addresses = 'localhost'`.** ACG·ufw 에도 5432 를 넣지 않는다 — 네트워크를 아예 타지 않는다
4. **타임존 `Asia/Seoul` 을 DB 에도 따로.** PostgreSQL 은 OS 시간대를 그대로 따르지 않는다.
   어긋나면 시세 "노후 판정"이 틀어져 멀쩡한 시세가 "시세문의"로 바뀐다
5. **문자셋 UTF8** (PGDG 기본). 상품명·주소가 한글이다
6. **메모리 배분** — `shared_buffers` 1GB / `effective_cache_size` 3GB, JVM 힙 상한 40%.
   한쪽만 올리면 OOM killer 가 둘 중 하나를 죽인다
7. **백업** 매일 04:00, 14일 (`/var/backups/pg`). `market_prices_effective`·`order_items`·
   `audit_logs` 는 append-only 라 복구 불가 시점이 곧 데이터 손실이다.
   복구 절차는 README 「배포 > DB 백업·복구」

> 함께 필요한 NCP 리소스: 앱 서버(Ubuntu), Object Storage(상품 이미지 + 백업 오프사이트),
> 도메인·SSL(A-5).

### E-6. GitHub Actions 자체 호스팅 러너 (배포)

**왜 이렇게 하나** — 개발자가 이동하며 작업해서 공인 IP 가 계속 바뀐다. ACG 의 22번
허용 IP 를 매번 고치는 것은 보안이 아니라 마찰이다. 자체 호스팅 러너는 서버에서
GitHub 로 **나가는** 연결만 쓰므로 22번 포트를 열 필요가 없고, 배포는 GitHub 버튼
하나로 끝난다(휴대폰에서도 된다).

⚠️ 러너는 운영 서버에서 저장소의 코드를 실행한다. **저장소 쓰기 권한 = 서버에서
임의 명령 실행**이라는 뜻이다. 비공개 저장소이고 접근 인원이 적다는 전제 위에 선다.
외부 기여자를 받게 되면 이 방식을 다시 봐야 한다.

#### 설치 (서버에서 1회, `hanseongge` 계정으로)

> ⚠️ 이 한 번만은 SSH 가 필요하다. 지금 접속이 막혀 있으면 NCP 콘솔에서 ACG 의
> 22번 허용 IP 를 현재 IP 로 한 번 고친 뒤 진행한다. 설치가 끝나면 다시는 필요 없다.

```bash
# GitHub > 저장소 > Settings > Actions > Runners > New self-hosted runner
# 에서 나오는 토큰을 쓴다 (토큰은 1시간 만료).
sudo -u hanseongge -i
mkdir -p ~/actions-runner && cd ~/actions-runner
curl -o runner.tar.gz -L https://github.com/actions/runner/releases/download/v2.328.0/actions-runner-linux-x64-2.328.0.tar.gz
tar xzf runner.tar.gz
./config.sh --url https://github.com/ettraveller/hansungge \
            --token <발급받은_토큰> \
            --labels hanseongge \
            --name hanseongge-prod --unattended
exit

# 부팅 시 자동 시작 (root 로)
cd /home/hanseongge/actions-runner
sudo ./svc.sh install hanseongge
sudo ./svc.sh start
sudo ./svc.sh status
```

`--labels hanseongge` 를 빼면 안 된다. 워크플로가 `runs-on: [self-hosted, hanseongge]`
로 이 러너를 지목한다.

#### GitHub 변수 등록

Settings > Secrets and variables > Actions > **Variables** 에 넣는다.
비밀값이 아니다 — 브라우저 번들에 그대로 보인다. 저장소에 두지 않는 이유는

### E-4. 본인인증 — KG이니시스 통합인증 「간편인증」

**2026-09-21 결정으로 「본인확인(03)」→「간편인증(01)」로 바꿨다.** 이니시스 회신: "네이버, 카카오, PASS, 삼성패스는
본인확인 인증서에 포함되지 않습니다." PASS 로 가입시키려면 간편인증이어야 한다. 간편인증은 **DI 를 주지 않고 CI 를 준다** →
같은 사람 판정은 CI 해시(`identity_key`)로 한다 (V23). 상세 검토는 `docs/본인확인_업체선택_정리.md`.

- 본인인증을 쓰는 곳: **휴대폰(자체) 가입 · 비밀번호 찾기 · 마이페이지 본인인증**(매입 신청·정산계좌 앞, 소셜 회원의 번호 등록)
- **소셜 가입은 본인인증을 받지 않는다.** 약관 동의로 끝난다 (만 14세 확인은 필수 약관으로 갈음)
- `IDENTITY_PROVIDER` 또는 `IDENTITY_HASH_PEPPER` 가 비어 있으면 위 세 곳만 닫힌다. 소셜 가입·로그인은 된다
- `MOCK` 은 로컬·개발 전용이고 `prod` 프로파일에서는 **기동이 실패한다**
- 정산: 설치비 없음, 성공 건당 과금, 익월 10일 세금계산서 → 계좌 입금 (자동이체·카드 불가). **단가·운영 MID 발급 기간 회신 대기**
- 기간이 2주를 넘기면 NICE평가정보로 전환 검토 — 공급자 인터페이스 뒤에 숨겨 두어 연동 부분만 바꾸면 된다

**운영 `/etc/hanseongge/api.env` 에 넣을 값**

```
IDENTITY_PROVIDER=INICIS
IDENTITY_MID=                     # 상점 아이디
IDENTITY_API_KEY=                 # 인증키(apiKey)
IDENTITY_REQ_SVC_CD=01            # 간편인증 (기본값)
IDENTITY_HASH_PEPPER=             # openssl rand -base64 48 — 한 번 정하면 절대 바꾸지 않는다
```

⚠️ **pepper 를 바꾸면** 이미 저장된 판정 키와 전부 어긋나, 가입한 사람이 다시 와도 알아보지 못한다. 서버를 옮길 때도
같은 값을 가져간다. 잃어버리면 되돌릴 방법이 없다 — 비밀 보관소에 따로 적어 둘 것.

**구현** — `InicisIdentityVerificationProvider`(요청 주소: 01 `https://sa.inicis.com/auth`, 03 `/id/auth`),
결과조회 주소는 `kssa/fcsa.inicis.com` 만 허용, SEED-CBC 복호화는 `InicisSeedCipher`. CI 는 `IdentityVerificationService` 에서
받자마자 `IdentityKeyHasher`(HMAC-SHA256)로 해시하고 버린다.

### E-3. 네이버 지도 API (지점찾기 `/store`)

지점 페이지의 지도가 이것 하나로 켜진다. **무료 사용량 안에서 쓸 수 있고 자동 발급이다.**

1. [NCP 콘솔](https://console.ncloud.com) → **Services → Application Services → Maps**
2. **Application 등록** — 이름은 아무거나 (예: `hanseongge-web`)
3. **두 가지를 함께 체크한다**
   - **Dynamic Map** — 지도 표시
   - **Geocoding** — 주소 → 좌표 변환. **이게 빠지면 지도가 안 뜬다** (아래 참조)
4. **웹 서비스 URL** 등록 — 여기 없는 주소에서 호출하면 거부된다
   - `http://localhost:3000` (개발)
   - `https://hanseongge.com` (운영)
5. 발급된 **Client ID** 를 프론트 환경변수에 넣는다

```
# frontend/.env.local (개발) — 운영은 배포 환경변수
NEXT_PUBLIC_NAVER_MAP_CLIENT_ID=발급받은_ID
```

`NEXT_PUBLIC_` 접두사라 **브라우저 번들에 그대로 노출된다.** 지도 Client ID 는 원래
공개되는 값이라 문제없지만, 그래서 **웹 서비스 URL 등록이 실질적인 보호장치**다.
등록을 빼먹으면 남이 우리 키로 지도를 쓸 수 있다.

#### Geocoding 을 함께 켜는 이유

지점 데이터에 위도·경도를 적지 않고 **주소를 지오코딩해서** 좌표를 얻는다.
지점마다 좌표를 손으로 찾아 넣으면 한 자리만 틀려도 엉뚱한 동네에 찍히고 아무도
모르며, 지점이 이전하면 주소와 좌표 두 곳을 고쳐야 한다. **주소 하나만 원천으로 둔다.**

지오코딩이 안 되는 주소(신축 건물 등)가 나오면 그 지점만 `branches.ts` 에
`lat`/`lng` 를 적어 덮어쓴다.

#### 키가 없는 동안의 동작

지도 자리에 안내 문구와 "네이버 지도에서 보기" 링크가 나온다. **임의의 기본 좌표로
지도를 띄우지 않는다** — 비어 있는 것보다 나쁘다. 고객이 틀린 위치를 맞다고 믿는다.

## I. 인증번호를 문자·이메일 중 고른다 (2026-09-23) — 남은 일

인증번호 받을 방법을 사용자가 고른다. 비밀번호 찾기는 **문자·이메일·본인인증** 셋 다 된다.
수단이 셋인 이유: 본인인증은 건당 과금이라 비밀번호를 잊을 때마다 부르면 비싸고, 문자·이메일은 싸지만
번호가 바뀐 사람은 쓸 수 없다.

| | 경로 | 조건 |
|---|---|---|
| 인증번호 로그인 | `POST /auth/code/send`·`/auth/code/login` | 이메일은 `email_verified_at` 이 찍힌 주소만 |
| 비밀번호 찾기 (인증번호) | `POST /auth/password/reset/code/send`·`/verify` | 목적이 `PASSWORD_RESET` 인 번호만 |

### F-1. 지점찾기, 레퍼런스와 다른 부분

| | 레퍼런스 | 현재 우리 | 왜 이렇게 뒀나 |
|---|---|---|---|
| 지역 필터 | **4열 격자 표**. 17개 시·도 전부, `충청북도 (0)` 처럼 0개도 표시 | 칩(알약) 나열, 지점 있는 지역만 | 시·도 17칸 중 16칸이 (0)이면 화면 대부분이 빈 정보다. **지점이 10개를 넘으면 격자 표로 바꾸는 것이 맞다** |
| 지도 | **전국 지도 일러스트**에 지점을 점으로 표시. 점을 누르면 상세지도 | 선택 지점의 네이버 지도 | 점 하나짜리 전국 지도는 "여기 한 곳뿐"만 강조한다. 지점이 전국에 퍼지면 이쪽이 훨씬 낫다 |
| 검색 | **검색 버튼**을 눌러야 실행 | 입력하는 대로 즉시 필터 | 지점 수가 적어 즉시 필터가 빠르다. 수십 개가 되면 버튼 방식이 나을 수 있다 |

### F-4. 회원관리 — 다음에 손볼 것

`/admin/members` 를 만들었다(목록·검색·상세·잠금 해제·이용정지). 지금 범위에서 뺀 것들:

| 항목 | 왜 뺐나 |
|---|---|
| 회원 비밀번호 초기화 | 관리자가 비밀번호를 정해 주면 <b>그 값을 전달하는 과정에서 새어 나간다.</b> 회원에게는 이메일 재설정 경로가 있다. 그 경로가 막힌 회원을 위해 "재설정 메일 보내기"를 관리자 화면에 두는 편이 맞다 |
| 회원 정보 수정 | 이름·생년월일·휴대폰은 본인확인 응답으로만 채워진다. 관리자가 손대면 "확인된 값"이 아니게 된다. 잘못됐으면 본인확인을 다시 받아야 한다 |
| 관리자에 의한 탈퇴 처리 | 탈퇴는 본인의 의사표시다. 이용을 막아야 하면 정지가 맞다. 서버도 거절한다 |
| 주문·문의 이력 연결 | 주문 도메인이 아직 없다. 문의는 붙일 수 있으나 회원 상세에서 게시판으로 넘어가는 동선이 먼저 필요하다 |
| 휴대폰 암호화 | `users.phone` 이 아직 평문이다 (아래 참조) |

**⚠️ `users.phone` 이 평문이다.** 설계서 §15 가 앱 계층 AES-256 을 요구하는데 구현되지
않았고, `User.java` 주석도 그렇게 적고 있다. 본인확인 도입으로 이 값이 "선택 입력값"에서
<b>검증된 필수 식별자</b>로 올라갔으므로 더 미룰 수 없다. 다만 암호화하면 지금 만든
휴대폰 검색(`LIKE`)이 동작하지 않는다 — 검색용 해시 컬럼을 따로 두거나 뒷자리만
별도 컬럼으로 빼는 설계가 함께 필요하다.

**PostgreSQL 함정 하나** — JPQL 에서 `:param IS NULL` 로 분기하면서 그 파라미터를
`lower()` 같은 함수에 넣으면, 검색어가 없을 때 타입 없는 null 이 바인딩되어
`ERROR: function lower(bytea) does not exist` 로 터진다. 회원 검색에서 실제로 겪었고,
"검색어 없음"을 빈 문자열로 바꿔 해결했다. `UserRepository.findAdminPage` 주석 참조.
